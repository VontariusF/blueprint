# vontariusf/blueprint

Begin with the Contextual Resolution Method. Research the problem. Define the solution. Give the build agent a blueprint.

Created by [Vontarius Falls](https://vontarius.xyz). [Overview and examples](https://vontarius.xyz/skills/blueprint/).

## Install

Requires Node.js 22.20 or later for the Skills CLI:

```sh
npx skills add vontariusf/blueprint --skill blueprint
```

The installer lets you choose your coding agent. Add `-g` for use across projects. Inspect the files and [UI reference credits](assets/ui-library/CREDITS.md) before installation.

## Use

Tell your agent: “Use Blueprint with the startup profile. Here is the problem I want to solve…”

Profiles: default, hackathon, startup. These are selectable planning presets, not separate native slash commands. Some hosts expose the local skill as `$blueprint`.

## Begin with the Contextual Resolution Method

Blueprint opens with the **Contextual Resolution Method (CRM)**, developed by Vontarius Falls. Work with your agent to define the problem, break down its parts and relationships, look into the surrounding context, and rethink the problem in light of the evidence. This discussion determines what the agent researches and why. An app, process change, service or adaptation of an existing system may be the response.

The resulting problem map, research findings and agreed boundaries lead into solution design, resources, visual direction, the full mockup set and delivery planning. Check the proposal against the original need, and return to earlier questions whenever evidence changes the understanding. All profiles follow this method; their emphasis and depth differ. See [the CRM workflow](references/contextual-resolution.md).

## What it produces

A project entry point linking the purpose, research, complete vision, scope, resources, user journeys, UI/UX mockups, critical path, decisions and observable completion criteria. For visual products, it requires actual image-generated mockups, full screen/state coverage, exact design contracts and a canonical reference pack. Confirmed references define a 1:1 visual and behavioral build target; a parity manifest tracks comparison evidence. Missing generation or approval keeps visual readiness incomplete. Scope adapts to the project. Every blueprint includes a resource/access register: required capabilities, scoped grants or keys, secure configuration references, owners, allocation limits, access requests and separate approval/configuration/verification states. Missing access blocks dependent execution, not independent design work.

## Choose the visual direction first

Blueprint discusses your visual preferences before generating concepts. When direction is unresolved, it normally creates three distinct image-generated variations of the same representative screen. Select one, combine elements, request refinements or suggest another direction. After you confirm the actual anchor reference, the agent expands every required tab, journey, state and responsive layout in that direction. Concept selection does not approve the later screens; the complete reference pack receives its own review. Research and functional planning continue while a direction decision is pending. Already confirmed project directions are reused.

## Keep the design consistent

Blueprint binds related screens and states to shared layout revisions, checks each image's app bounds and source-to-viewport mapping, and records inspections and approvals against the exact image hash. A durable pack record drives the current checkpoint so interrupted runs can resume without relying on stale summaries. The pack checker catches structural contradictions and outdated evidence. A companion handoff refresh updates the checkpoint, audit and shared status blocks together; its read-only final gate detects stale summaries, changed specification documents and outdated reconciliation evidence. A fresh substantive review is required after changes. Actual visual review and user confirmation remain necessary. See [canonical pack controls](references/canonical-pack.md).

## Reusable context

Supply your own designated resource inventory and style preferences. The included example is a schema, not live access. Project decisions stay local unless you designate them for reuse. No personal credentials, paths or infrastructure are included.

## Visual references

## Validation

Neutral trials exposed premature stopping and incomplete view coverage. After revisions, a fresh agent given the skill and an idea independently completed research, product questions, executable contracts, a resource/access register and 50 current image-generated references. Coverage included selected tabs for each role, journey outcomes, dialogs, responsive layouts and recovery states. A synthetic product owner reviewed exact images and explicit shared-component assemblies before design freeze. Runtime instructions remained unchanged during the trial; no reminders to create mockups or complete missing views were supplied.

A separate neutral resource reconciliation passed scoped checks for read-only grants, expired credentials, missing storage, approved-but-unconfigured access and denied production allocation. Earlier incomplete and credit-interrupted trials remain distinct from the completed run. These are specification-workflow checks, not evidence of application implementation, measured visual parity or live provider access. Further projects and agents may expose additional gaps.

A subsequent fresh neutral run exercised the concept-selection gate without reminders: three actual concepts, a combined revised anchor, scoped confirmation and 76 current image-generated references. It exposed remaining shared-layout drift and inconsistent screenshot framing. Workspace credit exhaustion interrupted the final audit reconciliation after generation completed, so that run remains a partial pass. This revision adds shared-layout comparisons, per-image capture contracts and a durable pack record/checker. These corrections receive targeted regression and packaging checks; they have not yet passed a new full neutral-agent run. No application implementation or measured visual parity is implied.

The next neutral trial independently selected a direction and produced 37 current, individually reviewed desktop/phone references, correcting several layout inconsistencies without reminders. It remained a partial pass: the checkpoint and audit fell behind, rendering was blocked and credits interrupted closeout. The current revision adds generated handoff summaries, document snapshots and a reconciliation gate bound to the current specification. These changes passed 23 focused handoff regression scenarios alongside the 17 existing pack scenarios; a new full neutral-agent trial is still required.

The handoff revision was then exercised end to end: a fresh agent completed 36 confirmed desktop/phone layout references and a final audit/handoff that passed independent checks. One earlier record edit left its checkpoint stale until the next batch refresh, so continuous checkpoint freshness remained a partial pass. This limitation is separate from the CRM methodology update.

The CRM-led opening workflow is a subsequent update. Earlier neutral trials do not validate this new entry phase; a fresh behavioral trial is still needed.
